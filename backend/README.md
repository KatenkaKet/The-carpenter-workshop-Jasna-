# Бэкенд «Ясна» — Go + Gin

Сервер REST API для детской столярной мастерской. Реализует обязательные маршруты [спецификации API](../endpoint.md): доступ мастера и родителей, семьи и дети, расписание, бронирование и переносы, посещаемость, тарифы, абонементы, счета, денежный журнал, ручные и тестовые онлайн-платежи, чеки, уведомления, аудит и CSV.

Стек: **Go 1.26, Gin 1.12, PostgreSQL 17, pgx 5**. Состояние хранится в PostgreSQL; имитации хранилища в памяти нет. В интеграционных тестах заменяется только внешний HTTP-сервис ЮKassa.

## Быстрый запуск

Из корня проекта:

```sh
cp .env.example .env
```

Задайте в `.env` собственные `POSTGRES_PASSWORD` и `MASTER_PASSWORD` (не менее 12 символов). `.env.example` предназначен для локальной разработки: HTTP и `COOKIE_SECURE=false`. Не публикуйте такую конфигурацию в интернете.

```sh
docker compose config --quiet
docker compose up -d --build db backend
curl --fail http://localhost:8080/healthz
```

Ответ проверки: `{"status":"ok"}`. API доступен по адресу `http://localhost:8080/api/v1`. Фронтенд запускается сервисом `frontend`: `docker compose up -d --build frontend`, адрес http://localhost:3000.

На старте сервер применяет миграции, создаёт учётную запись мастера, если такого логина ещё нет, и запускает фоновые задачи. Повторный старт не сбрасывает пароль существующего мастера. При ошибке конфигурации или миграции процесс завершается с ненулевым кодом.

Просмотр журналов и остановка без удаления данных:

```sh
docker compose logs --tail=100 backend
docker compose stop backend db
```

Для отдельного применения миграций:

```sh
docker compose run --rm backend migrate
```

Не применяйте `BD.sql` вручную для установки этого сервера: актуальная схема поставляется в миграциях. Историческая схема и существующие таблицы `public` не удаляются.

## Запуск без Docker для Go-приложения

Нужны Go 1.26 и доступная PostgreSQL 17. База должна быть создана заранее. Compose не публикует порт базы, поэтому для такого режима используйте отдельную локальную PostgreSQL или явно добавьте локальное перенаправление порта в собственный Compose override.

```sh
cd backend
export DATABASE_URL='postgres://jasna:your_password@localhost:5432/jasna?sslmode=disable'
export MASTER_LOGIN=master
export MASTER_PASSWORD='your_unique_long_password'
export APP_ENV=development
export APP_URL=http://localhost:3000
export ALLOWED_ORIGINS=http://localhost:3000
export COOKIE_SECURE=false
go run ./cmd/server
```

Сервер читает окружение; сам по себе файл `.env` Go-приложение не загружает. Docker Compose передаёт его значения через `environment`.

## Конфигурация

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Полная строка PostgreSQL; имеет приоритет над `DB_*`. |
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | Подключение к БД, если `DATABASE_URL` не задан. |
| `DB_SSLMODE` | По умолчанию `disable` для внутренней сети Compose; для удалённой БД настройте TLS. |
| `PORT` | Порт HTTP, по умолчанию `8080`. |
| `MASTER_LOGIN`, `MASTER_PASSWORD` | Первичное создание мастера. Логин от 3 символов, пароль от 12. Не меняют существующую учётную запись. |
| `APP_URL` | Адрес интерфейса; используется в персональных ссылках. |
| `ALLOWED_ORIGINS` | Разрешённые Origin через запятую; по умолчанию `APP_URL`. Без завершающего `/`. |
| `COOKIE_SECURE` | По умолчанию `true`. Значение `false` допускается только при `APP_ENV=development`. |
| `APP_ENV` | Для локальной разработки `development`, для сервера `production`. |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | Реквизиты тестового магазина, только на сервере. |
| `PAYMENT_RETURN_URL` | Страница возврата после оплаты. Возврат не является подтверждением платежа. |
| `PAYMENT_TEST` | Только `true`; запуск с реальными платежами намеренно заблокирован. |
| `RECEIPT_ALLOWED_HOSTS` | Разрешённые домены внешних чеков; по умолчанию `lknpd.nalog.ru`. |

## Вход и работа с API

Все изменяющие запросы из браузера передают разрешённый `Origin`. После входа дополнительно нужен `X-CSRF-Token` из ответа входа или `GET /auth/me` и cookie сессии.

Пример входа мастера с вымышленным паролем — замените его своим:

```sh
curl --fail-with-body -c /tmp/jasna-master.cookies \
  -H 'Origin: http://localhost:3000' \
  -H 'Content-Type: application/json' \
  -d '{"login":"master","password":"your_unique_long_password"}' \
  http://localhost:8080/api/v1/auth/master/login
```

Сохраните `csrf_token` из ответа и передавайте его при изменениях:

```sh
curl --fail-with-body -b /tmp/jasna-master.cookies \
  -H 'Origin: http://localhost:3000' \
  -H 'X-CSRF-Token: <csrf_token>' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Столярная группа","capacity":2}' \
  http://localhost:8080/api/v1/master/groups
```

Родительскую ссылку выдаёт мастер через `POST /master/families/:id/access-links`. Интерфейс должен извлечь токен из fragment `#token=...`, удалить его из адресной строки и отправить `POST /auth/access-link/exchange` с JSON `{"token":"..."}`. Email и пароль родителю не нужны. Сама страница `/access` относится к будущему фронтенду, сервер обслуживает только API.

Ссылки повторно используемые до истечения срока или отзыва. Выдача новой ссылки отзывает предыдущие ссылки семьи и все их сессии. Родительские сессии живут не более 30 дней и не дольше ссылки, мастерские — 12 часов. В БД хранятся хеши токенов и Argon2id-хеш пароля. Если одновременно переданы обе ролевые cookie, API возвращает `409 SESSION_CONTEXT_CONFLICT`; используйте разные профили браузера для демонстрации двух ролей.

Для `POST /bookings`, переноса, создания/отмены счёта, оплаты и корректировки абонемента передавайте `Idempotency-Key` длиной 8–200 символов. Повторяйте тот же ключ только с тем же телом запроса. Проверка сравнивает байты JSON: перестановка полей считается другим телом. Повтор возвращает сохранённый результат, другое тело — `409`.

Изменяемые объекты содержат `version`; PATCH и исправление посещаемости принимают `expected_version`. Для замены чека версия передаётся полем multipart. Конфликт версий возвращает `409 VERSION_CONFLICT`.

Списки возвращают `items`, `total`, `limit`, `offset`. Суммы — целые копейки. Даты диапазонов относятся к `Asia/Yekaterinburg`, граница `to` включительна. Полное описание входных данных и маршрутов — в [endpoint.md](../endpoint.md).

```text
backend/

├── internal/database/
│   ├── database.go                 # Пул подключений и миграции
│   └── migrations/001_init.sql     # Актуальная реляционная схема
├── internal/app/
│   ├── core.go                    # Транзакции, ошибки, идемпотентность, SQL-помощники
│   ├── router.go                  # Регистрация маршрутов Gin
│   ├── auth.go                    # Вход, cookie, CSRF, отзыв ссылок, лимиты
│   ├── catalog.go                 # Семьи, дети, группы, тарифы и правила
│   ├── schedule.go                # Занятия, запись, переносы, посещаемость
│   ├── finance.go                 # Счета, балансы, абонементы и ручные оплаты
│   ├── provider.go                # ЮKassa, сверка оплат, фоновые задачи
│   ├── files.go                   # Чеки, уведомления и CSV
│   └── app_test.go                # Модульные и интеграционные проверки
└── scripts/                       # Копирование и проверка восстановления
```

SQL-параметры передаются отдельно от значений. Имена таблиц и полей для изменений задаются обработчиками; неизвестные поля JSON отклоняются. Источником истины служит PostgreSQL, а не содержимое cookie или переданный родителем `family_id`.

## Транзакции и финансовые правила

Для небольшой мастерской выбран простой способ исключить гонки: каждая изменяющая транзакция получает одну общую PostgreSQL advisory-блокировку. Она действует между процессами сервера, включая фоновые задания. Ограничения уникальности и CHECK в БД дополнительно защищают активные записи, платежи и остатки.

Это сознательное отличие от более сложной схемы блокировок отдельных детей и занятий в первоначальном контракте. Длительные внешние HTTP-запросы к ЮKassa выполняются **после сохранения попытки оплаты и вне блокировки**. При увеличении нагрузки блокировку можно разделить по ресурсам, сохранив проверки конкурентности.

- Запись проверяет место, дубль и пересечение времени ребёнка. Перенос создаёт новую запись и отменяет старую в одной транзакции; при заполненной целевой группе исходная запись сохраняется.
- При записи сохраняется снимок правил. Изменение политики не переписывает историю. Мастерская отмена не списывает занятие.
- Счёт фиксирует цену и тариф. Покупка абонемента на четыре занятия создаёт денежное начисление; оплата погашает его и выдаёт четыре занятия ровно один раз.
- Денежный баланс и остаток занятий независимы. Посещение при оплаченном абонементе уменьшает только число занятий.
- Без подходящего абонемента посещение фиксируется с разовым счётом и задолженностью. Наличные и перевод вносятся мастером по счёту.
- Исправление добавляет обратное движение, не удаляет исходную запись. Отмена оплаченного разового начисления образует кредит семьи; восстановление отметки использует уже внесённую оплату.
- Отрицательное количество занятий запрещено. Кеш остатка обновляет один триггер при вставке движения.
- Денежный журнал, журнал занятий и аудит защищены от UPDATE/DELETE триггерами БД.
- Пока по счёту есть незавершённая онлайн-попытка, его отмена/компенсация возвращает `409 PAYMENT_IN_PROGRESS`. Сначала нужно дождаться подтверждения или сверки; это предотвращает неоднозначные расчёты.

## ЮKassa и СБП

Создание платежа: `POST /payments/intent` с `invoice_id`, `method=online|sbp` и ключом идемпотентности. Клиент не задаёт сумму. Сервер сначала сохраняет попытку и её ключ, затем обращается к ЮKassa; повтор после сетевого сбоя использует тот же ключ. СБП использует того же провайдера и переход по `confirmation_url`.

Если идентификатор платежа у провайдера не удалось получить за 23 часа, автоматическое повторное создание прекращается с `409 PAYMENT_RECONCILIATION_REQUIRED`; мастер получает уведомление о необходимости сверки. Это сохраняет запас до истечения [24-часовой гарантии идемпотентности ЮKassa](https://yookassa.ru/developers/using-api/interaction-format). Не создавайте новую попытку до проверки фактического результата старой в магазине.

Уведомления приходят на `POST /api/v1/webhooks/payments/yookassa`. Сервер получает актуальный платёж из API провайдера и проверяет сумму, валюту, магазин, тестовый режим и привязку к локальному счёту. Повторное событие не начисляет деньги или занятия повторно. Временная ошибка возвращает `503`, чтобы провайдер повторил доставку.

Подключение:

1. Задайте тестовые реквизиты в окружении и перезапустите backend.
2. Настройте доступный через HTTPS адрес webhook в тестовом магазине.
3. Подпишитесь на `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture`.
4. Пройдите оплату тестового счёта и проверьте кабинет через API.

Проверки в репозитории используют подменённый HTTP-ответ провайдера и настоящую PostgreSQL. Платёж через реальный тестовый магазин ещё требует ваших реквизитов и публичного HTTPS-адреса; такой платёж во время разработки не выполнялся.

Официальные источники: [уведомления ЮKassa](https://yookassa.ru/developers/using-api/webhooks), [оплата через СБП](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/manual-integration/other/sbp).

## Чеки и фоновые задачи

Чеки PDF/JPEG/PNG до 10 MiB хранятся в закрытой таблице PostgreSQL (`bytea`), а не в публичном каталоге. Проверяются содержимое файла и принадлежность платежа семье. Файл выдаётся через авторизованный endpoint с `Content-Disposition: attachment`. Замена сохраняет старые данные в `receipt_versions` и запись аудита. Внешние HTTPS-ссылки ограничены списком доменов; сервер их не скачивает.

Хранение чеков в БД упрощает копирование прототипа: один дамп включает данные, текущие чеки и историю замен. При большом числе файлов можно перейти на отдельное закрытое хранилище.

Внутри процесса раз в минуту выполняются:

- доставка уведомлений из транзакционного outbox;
- напоминания об окончании абонемента и открытых счетах с защитой от повторов за день;
- уведомления мастера о заканчивающихся абонементах;
- сверка незавершённых платежей, включая восстановление создания после сетевого сбоя;
- отзыв истёкших сессий и проверка согласованности остатков.

Проверка срока/отзыва сессии выполняется на каждом запросе. Задержка фонового задания не продлевает доступ. Новое уведомление может появиться в списке в течение следующего фонового цикла.

## Тесты

Из папки `backend`:

```sh
go test ./...
go vet ./...
```

Без `TEST_DATABASE_URL` интеграционный тест пропускается. Для полной проверки используйте **отдельную одноразовую БД**, имя которой начинается с `jasna_test`:

```sh
docker run --name jasna-test-db \
  -e POSTGRES_USER=jasna -e POSTGRES_PASSWORD=test_password \
  -e POSTGRES_DB=jasna_test -p 127.0.0.1:55439:5432 -d postgres:17
# Дождитесь: docker exec jasna-test-db pg_isready -U jasna -d jasna_test
TEST_DATABASE_URL='postgres://jasna:test_password@localhost:55439/jasna_test?sslmode=disable' \
  go test -race ./... -count=1
```

Интеграционный тест удаляет и создаёт схему `jasna` в указанной тестовой базе. Не передавайте ему рабочую БД.

Проверяются миграции, вход двух ролей, семья с двумя детьми, конкуренция за последнее место, восемь параллельных webhook, остаток 4 → 3, исправления и компенсации, защищённый чек, перенос с откатом при ошибке, разовая задолженность, ручная оплата и её повтор, CSV, уведомления, CSRF, версии и изоляция семей. Отдельный тест сопоставляет обязательные маршруты спецификации с маршрутизатором.

После проверки одноразовый контейнер можно удалить: `docker rm -f jasna-test-db`.

## Резервное копирование и сервер

Из корня проекта:

```sh
./backend/scripts/backup.sh
./backend/scripts/restore-check.sh /absolute/path/to/backup.dump
```

Первый скрипт создаёт закрытый файл в `backups/` и переименовывает его из `.partial` только после успешного `pg_dump`. Второй восстанавливает копию в новую проверочную базу, не заменяет рабочую, проверяет наличие таблиц/чеков и согласованность остатка. Проверочная база остаётся для осмотра.

Для регулярного копирования назначьте `backup.sh` через cron/таймер сервера и переносите копии за пределы этого сервера. Планировщик и внешнее хранилище зависят от вашего хостинга и автоматически не устанавливаются. Ограничьте доступ к дампам: в них есть персональные данные и чеки. CSV предназначен для анализа, а не восстановления приложения.

При восстановлении рабочей системы остановите backend, восстановите дамп в отдельную БД, проверьте данные и переключите подключение. До публикации отзовите восстановленные сессии и персональные ссылки, чтобы не восстановить старый доступ:

```sql
UPDATE jasna.sessions SET revoked_at = now() WHERE revoked_at IS NULL;
UPDATE jasna.access_links SET revoked_at = now() WHERE revoked_at IS NULL;
```

Для публикации нужны HTTPS и обратный прокси, направляющий `/api/` и `/healthz` на `127.0.0.1:8080`. Установите реальные `APP_URL`, `ALLOWED_ORIGINS`, `PAYMENT_RETURN_URL`, `APP_ENV=production`, `COOKIE_SECURE=true`. База и порт бэкенда по умолчанию не открыты во внешнюю сеть. Docker-образ запускается от непривилегированного пользователя.

Результаты выполненных проверок: [docs/backend-validation.md](../docs/backend-validation.md).

## Границы реализации

Обязательное API реализовано; фронтенд, самостоятельная первичная регистрация семьи, лист ожидания, отработки, импорт CRM, мессенджеры и интеграция ВК не входят в этот бэкенд первой версии. Автоматические чеки, возвраты, частичные оплаты и распределение кредита между счетами также не реализованы согласно принятому объёму прототипа.

Онлайн-платежи разрешены только в тестовом режиме. Лимиты запросов хранятся в памяти одного процесса; для нескольких публичных реплик потребуется общий ограничитель на прокси. Общая блокировка транзакций рассчитана на небольшую мастерскую. До эксплуатации с реальными семьями нужны настройка сервера, резервного копирования и проверка платёжной интеграции с вашим магазином.
