# Проверка мастерской, тестовая оплата и CSV

## Запуск

`docker compose up -d --build` из корня проекта. Интерфейс: http://localhost:3000.
При запуске автоматически применяются миграции. Пароль существующего мастера не меняется.

Локальная заглушка оплаты включается двумя настройками `.env`:

```dotenv
APP_ENV=development
PAYMENT_STUB=true
```

После изменения настроек пересоздайте backend: `docker compose up -d --build backend`.
Это отдельный режим без обращения к ЮKassa и без списания денег. В кабинете есть надпись «Тестовая оплата»; способ платежа в API/CSV — `test`. Он проходит тот же учёт счёта, абонемента и резервов, что подтверждённая оплата. Успешные тестовые платежи входят в статистику демонстрационного сервиса. Не используйте этот режим для реальных расчётов; `PAYMENT_STUB=false` отключает endpoint, а в `APP_ENV=production` он недоступен независимо от флага.

## Сценарий показа

1. В расписании создайте **групповое занятие**, вместимость **2**, любое корректное время и длительность. Время начала должно наступить к моменту отметки посещения: сервер не разрешает отмечать ещё не начавшееся занятие.
2. В «Клиентах» создайте семью с **двумя детьми**. Создайте персональную ссылку, скопируйте её и откройте в отдельном окне браузера. Выберите нужного ребёнка.
3. Запишите ребёнка на созданное занятие. Без прежнего абонемента доступен вариант **«Записаться, затем оплатить абонемент»**. Запись видна мастеру и в ближайших занятиях родителя.
4. Мастер создаёт тариф на **4 занятия** в «Абонементы → Тарифы и правила». Выбирать группу не требуется.
5. Родитель в «Тарифах» выбирает этого же ребёнка и тариф, затем нажимает **«Провести тестовую оплату»**. Должно появиться подтверждение тестовой оплаты. Счёт оплачен, у абонемента: всего 4, использовано 0, зарезервировано 1, доступно 3.
6. Когда занятие началось, мастер отмечает ребёнка «Посетил». Теперь: всего 4, использовано 1, зарезервировано 0, доступно/остаток **3**.
7. В «Финансах» прикрепите PDF/изображение или разрешённую ссылку на чек к этому платежу. Родитель открывает его в истории оплат. Чек необязателен для признания оплаты.
8. Для проверки вместимости запишите второго ребёнка на то же занятие **до его начала**. Попытка записать ещё одного ребёнка отклоняется сервером `409 SEAT_LIMIT_EXCEEDED`. Форма родителя при заполнении показывает отсутствие мест. Для третьей попытки нужен отдельный ребёнок — не создавайте демонстрационные данные в рабочей базе ради теста; этот случай уже покрыт изолированным автотестом.
9. Повторите `POST /api/v1/payments/test-confirm` с тем же телом и `Idempotency-Key`: вернётся тот же платёж. С новым ключом для уже оплаченного счёта — `409 INVOICE_NOT_OPEN`. Повторного начисления четырёх занятий нет.

Для проверки без ожидания реального времени используйте backend-интеграционный тест: он управляет часами только внутри изолированного приложения. Рабочие часы и данные не подменяются.

Наличный вариант: мастер оформляет/продлевает абонемент, выбирает «Наличные» и при необходимости прикрепляет чек. Создание счёта и успешной оплаты атомарно. Если загрузка чека не удалась, платёж остаётся подтверждённым, чек можно прикрепить позднее.

## Выгрузка

В «Клиентах», «Журнале посещаемости» и «Финансах» есть блок **«Выгрузить данные в CSV»**:

- **Клиенты и дети** — строка на ребёнка, данные родителя и семьи.
- **Посещения** — запись, занятие, ребёнок, отметка, списание, связанный абонемент/счёт.
- **Оплаты** — сумма в копейках, способ, статус, счёт, ребёнок, семейство и идентификатор чека.

Выгружается вся история. Аннулированные платежи сохранены со статусом `voided`; при внешнем подсчёте выручки берите только `succeeded`. CSV — UTF-8, разделитель запятая, первая строка содержит заголовки. Опасные значения для формул таблиц экранируются. Выгрузка доступна только мастеру.

API (cookie сессии мастера):

```text
GET /api/v1/master/export/children.csv
GET /api/v1/master/export/attendance.csv
GET /api/v1/master/export/payments.csv
GET /api/v1/master/export/all.zip
```

Необязательные параметры `from=YYYY-MM-DD&to=YYYY-MM-DD` ограничивают период посещений/оплат. Оплаты дополнительно принимают `status` и `method`, посещения — `group_id`.

## Данные и ограничения

- Группы убраны из тарифов и формы их создания. Существующие группы расписания не удалены.
- Миграция 003 снимает привязку сохранённых тарифов для будущих покупок. Ранее созданные счета, снимки тарифов и оплаченные абонементы сохраняют прежние условия. Новые тарифы из интерфейса универсальны. API сохраняет поддержку явного `group_id` для совместимости старых клиентов.
- Настройки отмены/пропусков/переносов теперь общие. После сохранения применяются ко всем группам, включая новые. До первого сохранения продолжают действовать прежние правила. История операций не пересчитывается.
- Предварительная запись без абонемента разрешена явно; после оплаты покрываются подходящие записи по дате в пределах количества купленных занятий. Лишние неподтверждённые оплатой записи не создают отрицательный остаток. Если абонемент уже был и исчерпан, эта опция не позволяет обойти лимит. Разовое занятие остаётся отдельным вариантом оплаты.
- Аннулирование наличной, переводной или тестовой оплаты сохраняет историю, открывает прежний счёт и приостанавливает абонемент. Использованные занятия не теряются. Для настоящей внешней оплаты требуется реальный возврат у провайдера.
- Родительская ссылка хранится в открытом виде только до перезагрузки страницы мастера. После перезагрузки можно отозвать старую и выпустить новую; отзыв блокирует уже выданную родительскую сессию.
