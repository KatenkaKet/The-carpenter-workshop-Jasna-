# Ясна — запись и учёт занятий

Веб-приложение для небольшой детской столярной мастерской «Ясна» в Сургуте. Помогает мастеру вести расписание, запись, посещаемость, абонементы и оплаты, а родителям — записывать детей и видеть расчёты без переписки.

Цель первой версии — полный цикл: **запись → оплата → посещение → списание занятия → просмотр остатка и чека**. Система должна работать самостоятельно, без обязательной подписки на CRM, и быть удобной на телефоне.

## Текущий статус

Реализован бэкенд на **Go + Gin** с PostgreSQL: обязательные API, миграция, Dockerfile, авторизация, бронирование, посещаемость, расчёты, тестовая интеграция ЮKassa, чеки, уведомления, аудит и CSV. Фронтенд ещё не реализован; полного пользовательского интерфейса пока нет.

Подробные инструкции: [документация бэкенда](backend/README.md), [схема БД и отличия от BD.sql](docs/database.md), [спецификация API](endpoint.md).

Интеграционные тесты используют настоящую PostgreSQL и подменённый HTTP-сервис оплаты. Проверка с вашим тестовым магазином ЮKassa и настройка публичного HTTPS требуют реквизитов и адреса сервера.

## Пользователи

| Роль | Возможности |
| --- | --- |
| Мастер | Создание расписания, управление семьями и записью, журнал посещаемости, настройка правил, учёт оплат, прикрепление чеков, экспорт и история изменений. |
| Родитель | Запись и отмена, ближайшие занятия, история посещений, абонементы, денежный баланс, оплаты, чеки и уведомления только своей семьи. В кабинете может быть несколько детей. |
| Посетитель | Просмотр публичного расписания и свободных мест по ссылке с сайта или из ВК. |

## Обязательные функции первой версии

- **Расписание и запись:** групповые и индивидуальные занятия, свободные места, отмена, защита от переполнения и повторной записи ребёнка.
- **Посещаемость:** «посетил», «пропустил», «отмена»; списание по правилам мастера; исправления с историей и обратными операциями.
- **Абонементы:** оплаченные и оставшиеся занятия, сроки действия, история списаний. Денежный баланс и задолженность отображаются отдельно от количества занятий.
- **Доступ родителя:** персональная защищённая ссылка без обязательной почты и пароля, отзыв и замена ссылки. Доступ мастера защищается отдельно.
- **Оплаты:** тестовая онлайн-оплата через ЮKassa, включая СБП, ручное внесение наличных и переводов. Начисление только после подтверждения; повторное уведомление не меняет баланс повторно.
- **Уведомления в кабинете:** запись, изменение и отмена занятия, окончание абонемента, необходимость оплаты; счётчик непрочитанных.
- **Чеки:** мастер прикрепляет файл или ссылку на чек из «Мой налог» к конкретной оплате; родитель открывает или скачивает его. Автоматическое формирование чеков не входит в первую версию.
- **Эксплуатация:** собственный сервер или недорогой хостинг, резервное копирование БД и файлов чеков, выгрузка клиентов, посещений и оплат в CSV.

Правила отмен, переносов и списаний должны храниться в настройках. Конкретные цены, сроки абонементов и условия отмены ниже не считаются утверждёнными правилами мастерской.

## Архитектура и структура проекта

- Бэкенд: Go 1.26 + Gin 1.12, pgx 5.
- База данных: PostgreSQL 17.
- Фронтенд: Vue 3 + TypeScript + Vite + Tailwind CSS; адаптирован из исходных экранов Chatium, подключён к API.
- Развёртывание: Docker Compose, три сервиса — `db`, `backend`, `frontend`.
- Авторизация: серверные сессии в защищённых cookie; отдельный вход мастера. Детали и проектные допущения описаны в API.

```text
.
├── backend/                 # Go + Gin, миграции, тесты, Dockerfile и документация
├── frontend/                # Vue-интерфейс, Nginx, браузерные проверки
├── compose.yaml             # PostgreSQL, backend и frontend
├── endpoint.md              # Скорректированная спецификация API 1.1
├── docs/
│   ├── endpoint-review.md   # Оценка исходного API и причины изменений
│   └── database.md          # Актуальная схема и отличия от исходной БД
└── README.md
```

Спецификация: [endpoint.md](endpoint.md). Разбор изменений: [docs/endpoint-review.md](docs/endpoint-review.md).

API: `/api/v1`. Время в интерфейсе — `Asia/Yekaterinburg` (Сургут, UTC+5), даты-время передаются с часовым поясом. Денежные суммы в API — целые копейки, валюта — RUB.

## Локальный запуск

Нужны Docker Engine и Docker Compose v2. Из корня проекта:

```sh
cp .env.example .env
```

Задайте собственные `POSTGRES_PASSWORD` и `MASTER_PASSWORD` (минимум 12 символов) в `.env`, затем:

```sh
docker compose config --quiet
docker compose up -d --build
curl --fail http://localhost:8080/healthz
```

API: `http://localhost:8080/api/v1`. Миграции применяются автоматически; мастер создаётся при первом запуске. Интерфейс: **http://localhost:3000/yasna**. Все три сервиса запускаются вместе. Nginx передаёт `/api/v1` бэкенду, сохраняя cookie и защиту CSRF. База доступна внутри Compose как `db:5432`, её порт наружу не опубликован. Данные сохраняются в томе `postgres_data`.

Настройки `.env.example` предназначены для локальной разработки. Для интернет-доступа нужны HTTPS, обратный прокси, реальные адреса интерфейса и `COOKIE_SECURE=true`; подробности — в [инструкции бэкенда](backend/README.md).

## Резервное копирование

```sh
./backend/scripts/backup.sh
./backend/scripts/restore-check.sh /absolute/path/to/backup.dump
```

Чеки и их предыдущие версии хранятся в закрытых таблицах PostgreSQL и входят в дамп вместе с остальными данными. Проверка восстановления создаёт отдельную базу и не заменяет рабочую. Хранение копий вне сервера и расписание копирования настраиваются на хостинге. CSV не заменяет резервную копию.

## Онлайн-оплата

Реализована интеграция с тестовым магазином ЮKassa, включая СБП, серверный расчёт суммы по счёту, проверку уведомлений через API провайдера и восстановление незавершённых попыток после сетевых сбоев. Повторное подтверждение не начисляет деньги и абонемент заново.

Для подключения задайте `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `PAYMENT_RETURN_URL` и настройте HTTPS webhook `/api/v1/webhooks/payments/yookassa`. Ключ не передаётся фронтенду. Реальные платежи отключены до реализации возвратов и согласования ограничений прототипа.

Порядок подключения и тестирования — в [документации бэкенда](backend/README.md). Источники интеграции: [уведомления ЮKassa](https://yookassa.ru/developers/using-api/webhooks), [СБП](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/manual-integration/other/sbp).

## Сценарий приёмки

Использовать только вымышленные данные и тестовые платежи.

1. Мастер создаёт группу на два места, занятие и семью с двумя детьми, выдаёт родителю персональную ссылку.
2. Родитель входит без email и пароля, видит обоих детей и записывает одного.
3. Родитель выбирает тариф на четыре занятия, получает счёт и проходит тестовую оплату. После подтверждения появляется абонемент с остатком 4.
4. Мастер отмечает посещение; остаток становится 3, денежный баланс не списывается повторно.
5. Мастер прикрепляет тестовый чек, родитель открывает и скачивает его.
6. Занять второе место; попытка записать третьего ребёнка из дополнительной тестовой семьи получает отказ. Повторная запись того же ребёнка также отклоняется.
7. Повторить уведомление об оплате, в том числе одновременно: остаются один платёж, одно начисление и остаток 3.
8. Исправить отметку на вариант без списания: остаток восстановлен, история сохранена. Проверить отмену и повторную запись, отзыв ссылки вместе с сессиями и недоступность чужих данных.
9. Проверить CSV, резервную копию и восстановление. Отдельно проверить ручную оплату и уведомления о продлении.

## Ограничения и результат передачи

Бэкенд и Vue-фронтенд запускаются локально через Docker Compose. Инструкция по кабинетам, проверкам и ограничениям интерфейса: [frontend/README.md](frontend/README.md). Публичный сервер и проверка ЮKassa с реквизитами мастерской остаются отдельными шагами.

Первая версия не включает автоматическую выдачу чеков, полноценную CRM, автоматические возвраты, частичные онлайн-платежи и взаимозачёт кредита между счетами. Эти ограничения нужно учитывать до использования с реальными оплатами.

Исходные `BD.sql` и `BD.svg` сохранены. Сервер использует отдельную схему `jasna` из миграции; перенос данных из старой схемы автоматически не выполняется. Подробности — в [описании базы](docs/database.md).
