# Проверка исходного endpoint.txt

> Историческая оценка спецификации до реализации. Текущее состояние сервера и проверки описаны в [документации бэкенда](../backend/README.md).

Проверка от 14 ноября 2026 года. Основание — требования пользователя и приложенный кейс «Система записи и учёта занятий для мастерской Ясна». Исправленная спецификация находится в [endpoint.md](../endpoint.md); исходный файл в «Загрузках» не изменён.

## Общая оценка

Исходник — хорошая основа для обсуждения: описаны роли, расписание, посещаемость, аудит, история движений абонементов, чеки, экспорт и настраиваемые правила. Однако использовать его как окончательное задание для реализации пока нельзя: несколько обязательных сценариев либо противоречат кейсу, либо допускают неоднозначную обработку денег и списаний.

Редакция 1.1 устраняет эти разрывы на уровне проекта API. Это не аудит работающего кода и не доказательство безопасности реализации: кода ещё нет.

## Найденные проблемы и изменения

| Приоритет | Проблема исходника | Что изменено |
| --- | --- | --- |
| Критичный | Вход только через email противоречит требованию «без почты и пароля». | Персональная ссылка семьи, необязательные контакты, отдельный вход мастера. |
| Высокий | Заявлен отзыв ссылки, но нет маршрутов её выдачи, отзыва и замены. | Добавлены маршруты мастера; отзыв распространяется на все связанные сессии. |
| Критичный | Webhook меняет статус оплаты, но не определяет начисление абонемента; в демо предлагается создать его вручную «или автоматически». | Счёт фиксирует покупку; оплата, денежное движение, выдача абонемента и начисление занятий атомарны. |
| Критичный | Родитель передаёт произвольную сумму и назначение платежа без тарифа и количества покупаемых занятий. | Добавлены тарифы и счета; сумму определяет сервер, платёж ссылается на счёт. |
| Критичный | ЮKassa приписан собственный HMAC-заголовок, СБП назван отдельным провайдером. | Проверка актуального платежа через API ЮKassa; СБП — способ оплаты через того же провайдера. |
| Высокий | `if succeeded` и уникальный внешний ID сами по себе не защищают два параллельных зачисления. | Блокировки, уникальные источники движений и единая транзакция; стабильный ключ при повторе запроса провайдеру. |
| Высокий | Денежный баланс и задолженность не имеют модели и маршрутов. | Добавлены денежный журнал, счета, остаток задолженности и семейная сводка отдельно от занятий. |
| Высокий | Посещение нельзя отметить без активного абонемента. Разовая оплата не связана с посещением. | При отсутствии абонемента создаётся разовый долг; оплаченный разовый счёт покрывает посещение. |
| Высокий | Отмена не запускает расчёт, а статус отмены родителем отсутствует в допустимых отметках. | Единая отметка `cancelled` с причиной; отмена сразу рассчитывает эффект по сохранённым условиям. |
| Высокий | При исправлении сравниваются статусы по текущим правилам, не фактические движения; время отмены не закреплено. | Снимки правил, `cancelled_at`, возврат в исходный абонемент, компенсации с ссылками на оригинальные операции. |
| Высокий | Одновременно описаны прямое изменение остатка и триггер, что может списать занятие дважды. | Единственный механизм обновления кеша через журнал; проверки остатка в транзакции. |
| Высокий | Полный UNIQUE на занятие и ребёнка блокирует повторную запись после отмены. | Частичный индекс только для активной записи и отдельная историческая запись при новом бронировании. |
| Высокий | Нет атомарного переноса ребёнка; правила переноса не определены. | Добавлен перенос с проверкой обоих занятий, сроков, места и конфликтов времени. |
| Высокий | Постоянный публичный URL чека обходит проверку прав после редиректа. | Закрытое файловое хранилище и скачивание через авторизованный маршрут. |
| Средний | Нет явного доступа мастера к общему списку платежей и редактирования семей/детей. | Добавлены соответствующие маршруты. |
| Средний | `number` для денег, неоднозначные ответы «409 либо заменить», «всегда 200» даже при сбое. | Копейки целым числом; определённые ответы; отдельная замена чека и повтор webhook при временном сбое. |
| Средний | Не описаны CSRF, конкурирующие правки, защита CSV от формул и правила выдачи секретов. | Добавлены требования к сессиям, Origin/CSRF, версиям объектов, экспорту и журналированию. |
| Средний | Оглавление и количество маршрутов не соответствуют содержимому; обязательное и дополнительное смешано. | Спецификация перегруппирована; лист ожидания вынесен в дополнительный этап без обещания готовности. |

## Важные решения редакции 1.1

Это предложенные решения для прототипа, а не факты о работе мастерской:

- Семью создаёт мастер и передаёт родителю ссылку. Новая семья без ссылки может посмотреть расписание, но самостоятельная первичная регистрация пока не предусмотрена.
- Родительская ссылка повторно используемая до истечения срока или отзыва. В базе хранится только её хеш. Мастер использует отдельную учётную запись.
- Абонемент закреплён за ребёнком и группой. Цены, длительность и условия отмены задаются мастером, не берутся из примеров как реальные.
- Продажа проходит через счёт, оплачиваемый целиком; после оплаты абонемент выдаётся автоматически. Продление оформляется новой покупкой.
- Переплата и компенсация оплаченного разового занятия отражаются кредитом семьи. Автоматическое распределение кредита и возврат средств требуют отдельного согласования и реализации. До этого прототип предназначен для тестовых оплат.
- Доступ к прикреплённому файлу чека защищён приложением; внешняя ссылка открывается в сервисе чеков, и возможность скачивания определяется этим сервисом.

## Проверка интеграции с ЮKassa

Официальное описание входящих уведомлений рекомендует проверять подлинность, например по статусу объекта или IP-адресу. Для проекта выбран запрос актуального объекта с серверными реквизитами и сверка с локальной попыткой; заголовок `X-Provider-Signature` из исходника удалён. [Документация уведомлений](https://yookassa.ru/developers/using-api/webhooks).

Для оплаты через СБП в ЮKassa используется способ `sbp` и подтверждение с переходом по `confirmation_url`; это не отдельный провайдер `/sbp`. [Документация СБП](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/manual-integration/other/sbp).

## Что ещё требуется при реализации

Перенести контракт в OpenAPI, создать миграции с ограничениями, реализовать обработчики и проверки доступа. Затем проверить демонстрационный сценарий, конкурентную запись на последнее место, параллельные повторы платежа, исправления посещений и восстановление копии. Текущая проверка касается документации; эти сценарии пока не запускались.
