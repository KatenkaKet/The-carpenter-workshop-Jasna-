# Аудит и план доработки мастерской

## Аудит

|---|---|---|
| Расписание | `frontend/src/screens/DayPage.vue`, `shared/use-demo.ts`; `backend/internal/app/schedule.go`; `jasna.groups`, `lessons` | Время и длительность ограничены только UI; индивидуальное занятие требует ребёнка в UI. Для отработки нужно поле БД. |
| Журнал | `JournalPage.vue`, `StarRating.vue`, `shared/demo.ts` | В API/БД оценок нет; остались вычисления и элементы UI. Удалить их без изменения посещаемости. |

| Абонементы | `finance.go`, `schedule.go`, `subscriptions`, `subscription_ledger` | Остаток меняется только при посещении; резерва нет. Нужны резервирование и атомарный переход в использование. |
| Клиенты / ссылки | `ClientsPage.vue`, `auth.go`, `access_links`, `sessions` | Ссылки хранятся только хешами; произвольное повторное копирование невозможно. Выданную ссылку можно копировать в текущей сессии; после перезагрузки выпускать новую с явным подтверждением. Отзыв API уже есть и проверяет сессии. Не хранить открытые токены в БД/localStorage. |
| Оплаты | `finance.go`, `InvoicesPanel.vue`, `FinancePage.vue` | Уведомление о счёте не исчезает после оплаты. Создание счёта и наличная оплата — две операции. Нужен единый транзакционный endpoint покупки, аннулирование ручных оплат с обратной записью в денежном журнале. |
| Чеки | `files.go`, `receipts`, `receipt_versions` | Есть загрузка и замена, нет снятия ошибочного чека. Мягкое удаление, аудит и закрытие доступа к файлу. |
| Родитель | `ParentSchedulePage`, `ManageBookings`, `ParentShell`, `App.vue` | Дубли ближайших занятий, общий confirm отмены, лишний выход, устаревшие суммы и уведомления. |

Все записи backend уже выполняет в транзакции под общим PostgreSQL advisory lock (включая фоновые обработчики). Его сохраняем: резерв и финансовые изменения получают такую же защиту от конкуренции. Существующие неподтверждённые изменения проекта сохраняются.

## Совместимые решения

1. `lessons_remaining` по-прежнему означает неиспользованные занятия. Резерв хранится отдельно, доступно = остаток − активные резервы. Резерв выбирается по ребёнку, группе и дате занятия, с ближайшим сроком окончания. Посещение превращает резерв в расход. Бесплатная отмена/неоплачиваемый пропуск освобождает резерв. Все повторы безопасны.
2. Существующие правила предусматривают разовое занятие в долг. Сохраняем этот сценарий как явный выбор `single_lesson`; при выборе абонемента исчерпанный остаток не превращаем автоматически в долг. Старые записи без достаточного покрытия сохраняются и отмечаются как прежние, без отрицательных остатков.
3. Аннулирование ручной оплаты открывает прежний счёт, приостанавливает абонемент и исключает платёж из выручки. Использованные занятия и связанные записи сохраняются. Повторная оплата того же счёта восстанавливает абонемент без повторного начисления. Подтверждённые внешние платежи требуют настоящего возврата у провайдера; этот API не симулирует возврат денег.
4. Немедленные настройки отмены/пропусков/переносов применяются к следующим операциям, включая будущие существующие записи. Исходные снимки правил и уже проведённые финансовые операции сохраняются. Реально применённое правило пишется в отметку/аудит.
5. «Скоро закончится»: доступен ≤1 урок либо осталось ≤3 календарных дней; истёкшие/исчерпанные показываются отдельно. Сортировка ФИО — русская локаль.

## Порядок

1. Миграция, резервирование, расчёт отмены, транзакционная покупка, аннулирование и снятие чека, фильтрация уведомлений.
2. Расписание и отработки; создание тарифов, правила, списки, ссылки, оплата с необязательным чеком.
3. Прозрачные счётчики и единый список записей родителя, серверный расчёт подтверждения отмены, синхронизация.
4. Интеграционные тесты на отдельной PostgreSQL БД, frontend-сборка и браузерные проверки без создания данных в рабочей БД.
